### 3.2 Root-Cause Analysis of Phase 22D Workload Discrepancy

In `backend/results/phase22/phase22d_shadow_deployment_summary.json` and the Phase 22D report:
- `operational_capacity.test_workload_pct` was reported as **7.36%**.
- `operational_capacity.incremental_precision_pct` was reported as **23.94%**.

**Audit Finding:** These two metrics came from two distinct, non-identical data partitions:
1. **$7.36\%$ Workload:** Calculated on the 5,000-record batch (`test_df.head(5000)`). Because the dataset is ordered by state code, this batch is restricted to States 1, 2, 4, 5, and 6 (Alabama, Alaska, Arizona, Arkansas, California). The degradation prevalence in this regional slice is only **$6.96\%$** ($348 / 5,000$), significantly lower than the national average ($8.91\%$). As a result, both models flagged fewer bridges ($5.06\%$ and $7.36\%$).
2. **$23.94\%$ Incremental Precision:** Calculated on the complete 65,580-record test set ($\Delta\text{TP} = +388, \Delta\text{Flags} = +1,621 \implies 388 / 1,621 = 23.9358\%$). On the 5,000-record slice, the actual incremental precision is **$20.87\%$** ($+24 / +115 = 20.8696\%$).
3. **Conclusion:** Both cohorts independently satisfy the operational criteria ($\text{Incremental Precision} \ge 20.0\%$), but reporting metrics across mismatched cohorts was a documentation error corrected in this audit.

## 5. Latency Discrepancy & SLA Benchmark

### 5.1 Reconciling the 0.04 ms Latency Artifact

In Phase 22D telemetry and reports, shadow latency was recorded as `0.04 ms (p95)`.

**Audit Analysis:**
- During `score_batch_with_shadow`, the total execution time for the 5,000-record NumPy matrix was measured (~$200\text{ ms}$) and divided by $5,000$, yielding an amortized duration of $0.04\text{ ms/record}$.
- While this accurately demonstrates vectorized batch throughput (~$22,000\text{ records/sec}$), it does **not** represent single-record request latency under realistic operational conditions.

### 5.2 Single-Record Inference Benchmarks

Rigorous benchmarking of 100 sequential single-record API requests (with cache warmup) revealed the actual operational latency:

| **Minimum Latency** | $6.30\text{ ms}$ | $7.81\text{ ms}$ | — | — |

| **95th Percentile ($p_{95}$)** | **$12.03\text{ ms}$** | **$14.24\text{ ms}$** | **$\le 15.0\text{ ms}$** | **PASSED** |
| **Maximum Latency** | $15.58\text{ ms}$ | $20.64\text{ ms}$ | — | Single spike |

**Audit Conclusion:** Both models comfortably satisfy the critical $p_{95} \le 15.0\text{ ms}$ SLA requirement. The Phase 22D report has been corrected to distinguish per-record latency from batch amortized speed.
